# 政企 VPN 客户端生态调研（背景与对标）

外部调研资料的整理版：原文是对各厂商公开资料的搜索摘要（2026-10 导出，HTML 格式），本文只保留对 v5vpn-rea-client 的定位、功能边界与架构决策有参考价值的部分，并逐条对到本项目现状。

## 1. 市场格局：两代客户端并存

| 厂商 | 传统 SSL VPN 客户端 | 零信任客户端 | 本项目 |
|:---|:---|:---|:---|
| 深信服 | EasyConnect（政企出镜率最高） | aTrust | **已支持**（v0.4.0 起，`internal/atrust`） |
| 网御星云 | 网御 SSL VPN 客户端 | 网御零信任客户端 | **已支持**（本项目主对象，`internal/protocol`） |
| 奇安信 | 网神 VPN / SecoClient | 可信访问客户端（SDP） | 未支持 |
| 华为 | SecoClient / AnyOffice | HiSec Endpoint | 未支持 |
| 新华三 | iNode 智能客户端 | H3C 零信任客户端 | 未支持 |
| 天融信 | TopConnect | 天融信零信任访问客户端 | 未支持 |
| 山石网科 | Hillstone Secure Connect | 山石网科零信任客户端 | 未支持 |

本项目卡位即表中前两行：传统线（网御 V5VPN）与零信任线（深信服 aTrust）各一条协议链，双后端并存、界面独立切换（见 [`architecture.md`](architecture.md)）。

## 2. 政企客户端的四大安全职责 vs 本项目边界

政企级客户端与普通商业 VPN 的差别在于：不止加密传输，还承担资产安全检查、身份多重认证、防泄密与统一管控。逐项对标：

| 能力 | 原厂客户端做法 | 本项目 | 说明 |
|:---|:---|:---|:---|
| 端点合规基线检查 | 联网前扫描防火墙 / 杀毒 / 补丁，不合规直接拒绝连接 | **不做** | 本项目是协议客户端，不接管终端合规 |
| 多因素认证 (MFA) | 短信 / 动态令牌 / 企业微信钉钉扫码 / 生物识别 | **已支持** | 因子链由网关动态编排，客户端不写死顺序，见 [`auth-flow.md`](auth-flow.md) |
| 网络沙箱与防泄密 | 沙箱内禁截屏 / 复制到个人应用 / 下载到 U 盘 | **不做** | 属终端管控范畴，与协议客户端正交 |
| 国密 SM2/SM3/SM4 | 内置国密组件，满足信创合规 | **未涉及** | 沿用网关既有 TLS / DES 链路，见 [`protocol.md`](protocol.md) |

## 3. 痛点对本项目架构的印证

调研列出的三大运维痛点，前两条是本项目的立项理由，第三条是数据面设计的直接约束：

| 痛点 | 原厂客户端表现 | 本项目对策 | 参照 |
|:---|:---|:---|:---|
| 跨平台兼容（信创生态） | 老客户端对统信 UOS、麒麟及 ARM 芯片（鲲鹏、飞腾）支持差，断连、装不上是常态 | 纯 Go + 系统原生 WebView（WebView2 / WKWebView / WebKitGTK），无平台专有依赖 | README §7 平台矩阵 |
| 浏览器组件依赖（ActiveX / JRE） | 老客户端依赖 IE 的 ActiveX 插件或老旧 JRE，Win11 抛弃 IE 后频繁报「无法初始化、找不到网卡驱动」；新一代已转向独立 Agent 或 HTML5 免客户端 | 独立 Agent：本地回环 HTTP 服务 + 内嵌 Web 前端，零浏览器插件 | [`architecture.md`](architecture.md) |
| 虚拟网卡驱动冲突 | 客户端安装 TUN/TAP 虚拟网卡，与多厂商 VPN 或虚拟机（VMware / VirtualBox）共存时驱动冲突，本地断网甚至蓝屏 | **全平台根除，不是绕过**：任何 OS 上本项目都不装虚拟网卡、不加载内核驱动——驱动冲突的载体不存在。代价是 NC（IPsec）资源需要替代承载：Windows 有（WSL2），其余平台暂无，见下表分平台速查 | [`web-proxy.md`](web-proxy.md)、[`ipsec.md`](ipsec.md) |

分平台速查（「痛点解决了没」的完整答案）：

| 平台 | 驱动冲突 | TCP/UDP 单端口资源 | 端口区间资源 | NC（IPsec）资源 |
|:---|:---|:---|:---|:---|
| Windows | ✅ 零驱动，无从冲突 | ✅ 本地端口映射 | ✅ 回环 CONNECT + 系统 PAC | ✅ WSL2 strongSwan 承载；路由只是 Windows 路由表条目，加解密在 WSL 内核 XFRM/ESP |
| Linux | ✅ 零驱动，无从冲突 | ⚠️ 代码全平台，未实测（README §7） | ⚠️ 本地代理可用；无系统 PAC，浏览器需 `--proxy-server` | ❌ 仅解析与展示 |
| macOS | ✅ 零驱动，无从冲突 | ⚠️ 同 Linux | ⚠️ 同 Linux | ❌ 仅解析与展示 |

- 驱动冲突一列全绿的原因：原厂把路由与加解密都放进内核驱动（`SecTap.sys` / `ndislwf.sys`），本项目两者都在别处——路由走 Windows 路由表条目，加解密走 WSL 内核 XFRM 或网关侧隧道，主机进程自始至终没有内核组件。
- **Windows 不装 WSL**：登录与其余资源完全不受影响；NC 资源降级为 `unavailable` 并提示一次性安装（`scripts/setup-ipsec-wsl.ps1`，需管理员 + 重启一次）。想不装 WSL 又要用 NC 资源，只能等 B 路线（用户态 IPsec，[`ipsec.md`](ipsec.md) §3）或网关侧改配。
- macOS / Linux 上 NC 资源的出路：用原厂客户端，或请网关管理员把账号资源改为 TCP/UDP 应用资源（[`ipsec.md`](ipsec.md) §4）；长期替代是用户态自实现 IPsec 的 B 路线（[`ipsec.md`](ipsec.md) §3），macOS 上需 utun。

## 4. 小结

- 双代并存的市场里，本项目覆盖出镜率最高的两家（网御、深信服），一条传统线一条零信任线；
- 四大安全职责中只承接 MFA，且实现为网关驱动的因子链（客户端不枚举流程），其余三项明确不在边界内；
- 三大痛点全部以架构规避：跨平台技术栈、无浏览器插件、无内核驱动——这三条同时也是本项目区别于原厂客户端的产品定位。
